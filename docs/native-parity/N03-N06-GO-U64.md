# Go exact-width execution APIs

`FuzzConfig64`, `GuidanceConfig64`, `CampaignConfig64` and corresponding
`FuzzReport64`, `GuidanceReport64`, `CorpusEntry64`, `JobReport64`,
`JobOutcome64`, `CampaignReport64` store count fields as `uint64`.
Defaults have matching `Default*64` constructors. Exact entrypoints are
`Fuzz64`, `FuzzWithLimits64`, `FuzzObserved64`, `GuidedFuzz64`,
`GuidedFuzzWithLimits64`, `GuidedFuzzObserved64`, `RunCampaign64`, and
`RunGuidedCampaign64`. Model, feedback, limits, metadata and observer types
are shared with existing APIs. A wide campaign sink accepts `JobReport64[I]`.
`Auto64`/`CampaignAuto64` use `AutoOptions64`; `Shrink64` and
`ShrinkWithLimits64` use `ShrinkConfig64` and return `ShrinkReport64` with
exact-width attempt counters and operation coordinates.

Existing exported APIs retain their original types and signatures. Their
implementations widen configurations and invoke these same exact kernels;
reports narrow only with checked conversions. `.Exact()` on legacy fuzz,
guidance and campaign configs and `.Legacy()` on exact fuzz/guidance configs
and reports reject invalid/unrepresentable values. They never clamp.
No configured case, step, corpus, or job bound is used as an eager allocation
size. Actual slice growth checks both native length and byte multiplication;
worker and result-channel counts narrow only after validation against 256
and 1024. Cancellation and semantic admission precede worker/channel
materialization. The private lifecycle and test-only codec use full-width
report counts; encoded lengths remain checked against actual bytes.

The normative boundary requirements are in `N03-N06-U64-CONTRACT.md`. This file
is an API integration note, not an executed qualification receipt. Installed
consumers should use the exact types for count operands above native MaxInt.
