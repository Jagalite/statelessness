# `paired-v1` candidate profile

Status: **experimental implementation candidate; not qualified**. Rust and the independent native Python, Go, TypeScript and Swift engines have
candidate implementations and application-level tests. The existing four qualified profile
claims and portable runner protocol remain unchanged. This document is version 1
of the candidate; promoting it requires independent specification review and
passing runtime qualification for every language being advertised.

## Contract

`paired-v1` builds on `core-v1`, `bfs-v1`, and `trace-json-v1`. It supplies a paired
model whose state is `(actual, independently advanced reference)`. The reference
accepts the same typed input as the actual reducer; it never receives actual
next-state, outputs, or disposition when advancing. Projections explicitly define
semantic equality of states and individual effects. Different native layouts and
codecs are allowed.

1. Initial history comes from the reference's initial state. Attaching a
   checkpoint requires both actual state and saved reference history; reconstructing
   history from actual state is outside this profile.
2. Each step executes the actual reducer and reference reducer on their respective
   previous states and the same input. A runtime observation wraps an already
   executed actual transition without executing the actual reducer again. If
   history advancement fails, the observation API retains that completed actual
   transition and exposes an error; it must not invent successful history.
3. State checks are actual checks, reference checks, then `pair.state` comparing
   projected states. Transition checks are actual checks, reference checks, then
   `pair.effects` comparing the ordered projected effect sequence, then
   `pair.outcome` comparing the complete disposition including its reason.
   Reference transition recomputation is permitted because reducers must be pure.
4. Check order, IDs, status, failure phase, the complete failing batch, and bounded
   work counts are normative. Diagnostic mismatch text uses language-specific
   value formatting and is not cross-language normative. Exact replay within one
   implementation still compares the recorded diagnostic text according to its
   ordinary trace contract. Duplicate user check IDs remain ordered observations,
   matching `core-v1`; adapters do not collapse or silently bless them.
5. The existing recorder stops after the first failing batch. Existing finite BFS
   observes combined state equality: differing reference histories cannot merge
   solely because actual state matches. Exhaustion, state/edge/depth bounds, skipped
   checks, and callback failures retain the `bfs-v1` meanings. This adds no fairness,
   wall-clock, external scheduler, or unbounded correctness claim.
6. Persistence frames both independent checkpoints using `ORC1`, then an unsigned
   64-bit little-endian actual byte length and bytes, then an unsigned 64-bit
   little-endian reference length and bytes. Unknown magic, truncation, excessive
   component lengths and trailing data are framing errors. Raw checkpoint decoding
   delegates component validation to the supplied decoders; applications requiring
   canonical raw checkpoints must supply strict decoders or compare re-encoding.
   Exact trace replay rejects noncanonical initial checkpoint/input encodings by
   decoding and re-encoding, and compares subsequent states against recorded bytes.
   No allocation is based on an unchecked declared length. `ORC1` itself has no
   identity or quota envelope: semantic identity validation and payload, item and
   step limits belong to the trace API. Callback allocation is not a process-memory
   guarantee. Framing is shared with the Rust `WithOracle` codec; this is not an
   implementation of Rust's complete binary `.sttrace` envelope in the native ports.
7. Identity includes actual, reference and projection semantic identities and
   builds. Length prefixes count UTF-8 bytes. Build-mismatch permission never
   authorizes model, properties, codec, or projection semantic changes. See the
   implementation metadata construction for the existing `with-oracle-v1` and
   `paired-v1` identity spelling, retained without changing Rust compatibility.
8. Unsupported profile/adapter operations must be explicit errors or unsupported
   status. They cannot be substituted with a passing or empty result.

## Application fixture and independent expectations

`conformance/paired-v1.tsv` is a hand-authored golden table, not generated by a Rust
run. The native Python, Go, TypeScript and Swift tests read it; Rust tests include
the same bytes. Its
columns map directly to `paired-v1.schema.json`. The table deliberately specifies
only portable observations. No reducer uses a table interpreter.

The actual reducer has a two-slot queue of binary values and textual effects. The
reference reducer uses base-three digits with the oldest value in the least
significant digit and numeric effects. Inputs are ordered `[put(0), put(1), take]`
at every state. Full puts reject with `full`; empty takes ignore with `empty`.
Successful puts emit `[10 + value, 20 + new_length]`; takes emit
`[30 + value, 20 + new_length]`. All effects are projected to numbers.

There are exactly seven queue contents: empty, two length-one queues, and four
length-two queues. Three inputs per content produce 21 edges, including rejected
and ignored revisits. Thus sufficiently bounded enumeration must exhaust at seven
states and 21 transitions. The exact edge budget of 21 must still exhaust. Golden
mutations independently exercise changed next-state, swapped effects, omitted
effects, changed ignored reason, and mismatched initial history. Boundary cases
exercise depth zero/one, state cap, and edge cap. Separate tests cover check order,
midstream restart, exact failure replay, strict semantic identities despite build
override, malformed checkpoints, observation errors, and native trace limits.

A native-language test result does not substitute for Rust runtime evidence.
Compilation of the Rust shared-golden suite is useful but does not qualify parity.
Submit builds through Kyoto and inspect its effective command: a compile-only
result is not a runtime pass. Record any separately authorized execution distinctly.

## Version and deprecation policy

Candidate semantics may change before qualification, with an explicit change entry
here and regenerated qualification evidence. After promotion, changing any
normative observation, ordering, identity, framing, or termination rule requires a
new profile name/version. Existing fixtures and readers remain available for the
documented support window; absence of an older reader is explicit unsupported.
Qualified profile lists must name exact versions and may expand only after every
required positive and negative case passes for that implementation.
